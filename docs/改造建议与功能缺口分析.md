## 1. 文档目的

本文档记录对当前工程（页面改造完成后）的功能性分析结论，包含：

- 当前各项目的功能实现程度。
- 功能缺口与不合理设计的清单（按风险分级）。
- 建议的改造批次、涉及文件与验收要点，用于排期、分工和版本验收。

本文档不替代 [软件功能说明](软件功能说明.md)。功能状态判定仍以该文档为准，本文档只描述“应当改什么、为什么改、改完怎么验收”。

## 2. 结论摘要

1. **页面改造已完成，但核心业务入口错位**：通用主程序当前只有 `DeveloperOptionsView` 能启动刷写，"固件刷写"页只能连接设备。
2. **配置声明与执行能力脱节（最高风险）**：BOOT 配置中已声明 CRC/擦除等元数据，执行器从不读取，导致“刷写完成”不足以证明固件正确。
3. **`DiagnosticFlashTool.Application` 能力最完整却被主程序绕过**：`App.csproj` 不引用 `Application`，因此主程序没有周期 Tester Present、没有算法注册、没有参数校验保护。
4. **旧版关键业务能力缺失**：回滚、断点续传、RSA2048 签名、指纹写入、预/后编程条件、状态回读全部未迁移。
5. **存在架构性重复**：两套刷写编排、两套 MVVM 基础设施、两份报文表、两套配置根目录。

## 4. 功能盘点

| 业务域 | 已可用 | 半通 / 缺失 |
| --- | --- | --- |
| CAN 连接 | Mock/ZLG 连接、断开、状态与日志 | 自动连接、波特率自动搜索为死设置；无 Kvaser；未知波特率静默降级为 500K |
| 配置管理 | 项目/BOOT/算法目录的增删改查与持久化 | CAN ID 不校验数值与 11/29 位范围；固件路径不校验存在性；`AppStartAddr/AppEndAddr` 从未使用 |
| 固件解析 | S19/SREC/MOT、Intel HEX、BIN | 解析器宽松：HEX 忽略记录类型、S19 不校验记录数 |
| 刷写执行 | 普通 UDS 步骤、0x27、0x34/0x36/0x37 分块下载 | 无擦除、无 CRC/签名校验、无指纹、无回滚、无断点续传、无 Tester Present、无取消、无重试 |
| 刷写操作 | 项目选择 + 开始刷写（位于开发者选项） | 无固件必选校验；无刷写清单预览与二次确认；进度按步数均分 |
| 报文监控 | 手工发帧、监控表、过滤、暂停、清空、CSV 导出 | 报文表在"开发者选项"与"刷写监控"重复两份 |
| 日志 | 内存日志、级别/关键词/时间筛选、文件轮转 | 级别靠中英关键词推断；文件写入异常被静默忽略 |
| 追溯 | 无 | 历史记录页为空壳；无刷写记录、操作员、固件哈希、DID 版本 |
| 权限 | 管理员模式认证与状态展示 | 状态未绑定任何权限，密码硬编码于客户端 |
| 生产/工位 | 无 | `Production/`、`Workspaces/` 为空目录 |

## 5. 功能缺口与不合理设计

### 5.1 P0：影响“刷写是否可信”

| 编号 | 问题 | 证据 | 风险 |
| --- | --- | --- | --- |
| GAP-001 | BOOT 配置声明 `crcAlgorithm`/`eraseRoutine`/`verify`/`receive`，执行器全部忽略 | `FlashFlowExecutor` 未读取上述字段；`CNHTC.json` 已声明 `CRC16_DNP` | 刷写成功不代表固件正确；不满足安全与合规要求 |
| GAP-002 | 同一问题在 EcuX 侧以抛异常方式处理 | `FlashSessionOptions.Validate()` 抛 `NotSupportedException` | 配置与实现不一致，用户无法通过配置表达真实需求 |
| GAP-003 | 主程序刷写无周期 Tester Present | `App.csproj` 不引用 `Application`；`TesterPresentScheduler` 未被 App 使用 | 长下载中 S3 超时导致会话掉线、刷写中途失败 |
| GAP-004 | 无刷写取消入口 | `MainViewModel` 无 `CancellationTokenSource`/取消命令；`StartFlashAsync` 的取消分支 UI 不可达 | 长流程无法终止 |
| GAP-005 | 取消/失败后无收尾 | 下载中断后不发 `0x37`/复位 | ECU 可能滞留编程会话 |
| GAP-006 | 无擦除例程 | `FlashStepConfig.EraseRoutine` 从未被消费 | 部分 ECU 无法完成刷写 |
| GAP-007 | 无 CRC/签名校验与回读比对 | 无 `31 01 F204` 等校验例程；旧版有 `needCRC` 与 `Rsa2048Pkcs1V15Sha256` | 无法验证刷写结果 |
| GAP-008 | 无失败恢复与回滚 | 旧版 `RollbackExecuter`（`22 E174/E172/E173` + `31 01 E174`）未迁移 | 刷写失败后 ECU 可能不可用 |
| GAP-009 | 无断点续传 | 旧版 `FileDownload` 的 `22 E180` 查询、跳块、裁剪擦除区间未迁移 | 断电/中断需整包重刷 |
| GAP-010 | **缺少运行时数据注入机制** | BOOT 节点 `extend` 为静态字符串；旧版有 `needCRC`、`asciiString` 与 JSON flow v3 的 `${var}`、`:u32be` 表达式 | CRC 结果、日期、设备标识、256 字节签名无法表达，是补齐 GAP-006/007/011 的前置条件 |
| GAP-011 | 无指纹写入与编程计数 | 旧版 `FingerPrint`（`2E F184` 写日期 + ASCII 设备标识）未迁移 | 产线留痕断链 |
| GAP-012 | 无预/后编程条件检查 | 旧版有 `31 01 0203` 预条件、`22 E170` 状态回读；新版 BOOT 仅有 `31 01 FF01` | 不满足 ECU 编程前置要求，无法确认编程生效 |
| GAP-013 | 固件非必选导致假成功 | `LoadFirmwareSet` 对不存在文件静默跳过，空 `FirmwareSet` 仍返回"刷写完成" | 存在“无下载却成功”的生产风险 |
| GAP-014 | 无 ECU 版本读取与刷写后核对 | 无 `22 F189/F191`、`22 F1xx` 读版本步骤 | 无法确认目标软件版本 |

### 5.2 P1：入口与交互设计不合理

| 编号 | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| DSG-001 | 刷写主入口位于"开发者选项" | 仅 `DeveloperOptionsView.xaml` 绑定 `StartFlashCommand` | 首页无开始按钮，用户找不到主流程（对应 LIMIT-001） |
| DSG-002 | 三页职责重叠 | "固件刷写"/"刷写监控"/"开发者选项"均展示设备与下载状态、进度 | 同一状态三处显示，报文表两份，维护成本翻倍 |
| DSG-003 | 进度模型按步数均分 | `FlashFlowExecutor` 使用 `stepStartPercent = index * 100 / flow.Count` | 下载步骤耗时长但占比低，进度条长时间停滞；旧版有计时与传输明细 |
| DSG-004 | 状态与业务耦合 | `ClassifyStatusText` 按关键词推断日志级别；`DownloadStatusKind` 用 `Warning` 表示"已取消"；`DatabaseStatusText` 恒为"数据库已连接" | 审计不可靠，存在假状态 |
| DSG-005 | EcuX 靠解析中文日志反推步骤状态 | `ProductViewModel.TryParseStepId`、`Contains("completed")` | 文案改动即静默失效 |
| DSG-006 | 失败仅写日志，无对话框与处置引导 | `ConnectAsync`/`StartFlashAsync`/`SendManualFrameAsync` | 操作员无明确处置指引 |
| DSG-007 | 误导性文案与硬编码 | "待自动搜索"（无此功能）、"BTMS 刷写监视器"、"通信协议 CAN" | 验收时真假能力难辨 |
| DSG-008 | 无刷写清单预览与二次确认 | 旧版有"刷写清单"表（状态/起始地址/长度/类型） | 误刷风险 |
| DSG-009 | 死代码页面 | `FunctionCheckView`（`Task.Delay` 假检测）、`RecipeConfigView` 未挂载 | 代码臃肿，易被误认为已交付功能 |
| DSG-010 | 无进度时间预估与传输明细 | 旧版显示计时与 36 字节进度明细 | 现场无法判断是否卡死 |

## 6. 建议改造批次

批次划分原则：先保证“刷写可信”，再保证“好用”，然后补“产线能力”，最后做“工程加固”。

### 第 1 批：正确性与安全性（发布阻断项）

目标：让“刷写完成”重新等于“固件正确”。

| 编号 | 任务 | 涉及文件 | 验收要点 |
| --- | --- | --- | --- |
| B1-01 | 让 `App` 引用 `Application`，删除 `MainViewModel` 内自建编排，改走 `FlashSessionService` | `DiagnosticFlashTool.App.csproj`、`ViewModels/MainViewModel.cs` | 主程序刷写期间存在周期 Tester Present；参数变更触发重连校验 |
| B1-02 | 在 `Core` 补 `RoutineControl(0x31)`、擦除、校验、读数据、指纹能力，并让 `FlashStepConfig` 的 `eraseRoutine`/`crcAlgorithm`/`verify` 真正被执行 | `Core/Flashing/FlashFlowExecutor.cs`、`Core/Configuration/BootConfig.cs` | 声明 `crcAlgorithm` 的节点会实际下发校验例程；Mock 流程可验证 |
| B1-03 | **短期兜底**：未实现期间，保存与加载 BOOT 流程时禁止声明 `eraseRoutine`/`crcAlgorithm`/`verify`/`receive` | `Core/Configuration/`、`App/ViewModels/MainViewModel.cs` | 配置校验给出明确错误，不再静默忽略 |
| B1-04 | BOOT 模型引入变量/表达式参数（`${crc}`、`${date}`、`${deviceId}` 等） | `Core/Configuration/BootConfig.cs`、`FlashFlowExecutor` | CRC、日期、签名可注入节点参数 |
| B1-05 | 固件必选校验（Driver/Application 开关）+ 空固件必须失败 | `FlashSessionOptions`、`MainViewModel.LoadFirmwareSet` | 缺失固件时刷写被拒绝，不返回成功 |
| B1-06 | 取消链路打通：UI 取消按钮 + `CancellationTokenSource` + 可取消的 DLL 调用 | `MainViewModel.cs`、`Views/DeveloperOptionsView.xaml`、`Infrastructure/Security/DllSeedKeyAlgorithm.cs` | 刷写可主动取消，取消后停止后续步骤并显示"刷写已取消" |
| B1-07 | 取消/失败收尾：补发 `0x37`/复位，避免 ECU 滞留编程会话 | `Core/Flashing/FlashFlowExecutor.cs` | 取消或失败后 ECU 可重新进入默认会话 |

## 7. 批次依赖与建议顺序

```mermaid
flowchart LR
    B1[第1批 正确性与安全] --> B2[第2批 工作流与可用性]
    B1 --> B3[第3批 恢复与产线能力]
    B2 --> B3
    B3 --> B4[第4批 工程加固]
    B1 --> B4
    B4 --> B5[第5批 文档同步]
```

- **B1-01 与 B1-03 优先**：改动集中、收益最大，且不涉及协议实现改动。
- **B1-04 是 B1-02、B3-02、B3-04 的前置条件**：没有变量注入能力，CRC/签名/指纹无法表达。
- **B2-01 与 B1-06 建议同期**：合并页面时一并接入取消按钮，避免二次返工。
- **B3 需要目标 ECU 通信矩阵确认**：DID、例程 ID、地址范围须以正式 BOOT 规范为准，不能沿用旧版示例值。
